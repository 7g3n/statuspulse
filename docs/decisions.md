# 設計判断の記録

採用した案だけでなく、**採らなかった案とその理由**、および**判断が変わる条件**を残す。

---

## 1. 「観測」と「判定」を別の場所に持つ

**決定**: 1回のリクエストの結果は `checks.result`（観測）に、監視対象を今どう扱うかは `monitors.current_status`（判定）に置く。判定は観測から導く。

**採らなかった案**

- _`checks` に最終的な状態だけを書く_ — 最も単純。だが「1回のタイムアウトでダウンと言い切らない」を後から入れるとき、過去の行の意味が変わってしまう。誤検知対策を入れる前と後で、同じ列が別のことを表す状態になる。
- _状態を持たず、毎回直近N件から計算する_ — キャッシュのずれは起きないが、一覧のたびに全対象ぶんの走査が要る。加えて「いつ状態が変わったか」を別に持たないと「3時間ダウン中」が出せない。

**理由**: 判定の規則は運用しながら必ず変わる（Phase 2 で連続N回失敗に変える）。一方、観測は事実なので後から変わらない。変わるものと変わらないものを同じ列に載せない。

**代償**: 2つの整合を保つ責任が生まれる。これは `record_check()` を唯一の書き込み経路にし、`checks` への直接の書き込みを RLS と GRANT で塞ぐことで対処した。

---

## 2. 判定の閾値は Phase 1 から列として持つ

**決定**: `monitors.failure_threshold` を Phase 1 の時点で作り、既定値を 1 にする。判定関数 `nextMonitorState()` も最初から閾値を引数に取る形で書く。

**理由**: Phase 2 の「連続N回失敗でダウン」は、この設計では**設定値の変更**でしかない。閾値を後から足すと、状態遷移の判定を書き直すことになる。列1つとテスト数件を先に持つ方が、後の書き直しより安い。

Phase 1 の画面では閾値を編集させない。使う予定のない設定項目を並べても、利用者が判断できることは増えない。

---

## 3. Cron Triggers は1本だけ置き、間隔の判定は DB で行う

**決定**: `crons = ["* * * * *"]`（毎分）の1本にして、「今チェックすべき対象はどれか」は `due_monitors()` が決める。

**採らなかった案**

- _間隔ごとに cron 式を分ける（1分用 / 5分用 / …）_ — 一見素直だが、監視対象の間隔を変えるたびに Worker の設定を書き換えてデプロイすることになる。画面から変えられる設定が、実際にはデプロイなしでは反映されない。
- _Worker が全対象を取得し、メモリ上で絞る_ — 対象が増えるほど、毎分の起動で全件を運ぶことになる。絞り込みは索引の効くところでやるべき。

**理由**: 「いつ実行するか」は監視対象ごとの設定であって、インフラの設定ではない。設定がある場所と判定が起きる場所を一致させる。

**代償**: 毎分の起動が必ず1回の問い合わせを発生させる（チェック対象が0件でも）。この程度の頻度なら無視できる。

---

## 4. due 判定を半周期ぶん早める

**決定**: `due_monitors()` の比較を `last_checked_at <= now() - (interval - 30秒)` とする。

**理由**: Cron の起動時刻には数秒のぶれがある。厳密に `>= interval` で比較すると、1分間隔の対象で経過が 59.4 秒になった回が飛ばされ、次の起動まで待つ。これが毎回起きると、**1分間隔の監視が実質2分間隔として動く**。

早めることでごく稀に間隔がわずかに詰まるが、「設定した間隔より粗くなる」方が監視ツールとして明確に悪い。

**判断が変わる条件**: Cron の起動周期を変えたとき。許容幅は起動周期の半分という関係で決めているので、両方を一緒に変える必要がある（`CRON_PERIOD_SECONDS` と `DUE_TOLERANCE_SECONDS`）。

---

## 5. 稼働率は「チェック回数ベース」で定義し、取りこぼしを併記する

**決定**: 稼働率 = 成功したチェック回数 ÷ 実行したチェック回数。あわせて「期待される回数に対して何回実行できたか」を計算し、9割を下回ったら画面に注意を出す。

**採らなかった案**

- _時間ベース（ダウンしていた期間の合計 ÷ 対象期間）_ — 定義としてはこちらが正しい。しかし Phase 1 にはダウンタイムの「期間」を持つテーブルが無く、チェックの点列から期間を復元するには、落ちた時刻と直った時刻の間をどう埋めるかという別の判断が要る。Phase 2 でダウンタイム履歴を作るときに、そこで一度に決める。

**この定義の弱点を明示する**: 分母は「実行できたチェック」しか数えない。**定期処理そのものが止まっていた時間は、分母からも分子からも消える**。その間に監視対象が落ちていても稼働率には表れず、実態より良い数字が出る。

監視ツールが黙って良い数字を出すのは最も避けたい挙動なので、`checkCoverage()` で期待回数と実測回数を突き合わせ、足りなければ稼働率の隣に警告を出す。

**判断が変わる条件**: Phase 2 でダウンタイム履歴（`incidents`）を持った時点で、時間ベースの稼働率に移す。

---

## 6. 稼働率の表示は四捨五入せず切り捨てる

**決定**: `formatUptimePercent()` は必ず切り捨てる。100% と表示するのは失敗が1回も無かったときだけ。

**理由**: 10000 回中 1 回落ちていれば 99.99% だが、小数第1位で四捨五入すると 100.0% になる。**落ちた事実があるのに 100% と表示される**のは、稼働率という数字への信頼そのものを損なう。

この種の数字は「良く見せない」方向に倒す。悪い方向の誤差は利用者が確認しに行くだけだが、良い方向の誤差は見過ごされる。

---

## 7. 集計を Phase 1 から DB のビューに置く

**決定**: 稼働率の集計は `monitor_overview` ビュー（`security_invoker = on`）で行う。

**理由**: 同じ開発者の StockDesk では Phase 1 の集計をクライアント側に置き、「表示のために全件を取得しなければならなくなったら DB へ移す」という条件を書いた。StatusPulse はその条件に**最初から当てはまっている**。7日ぶんのチェックは1分間隔の対象1つで1万行を超える。

早すぎる最適化を避けるという原則は、データ量の見積もりが変われば結論も変わる。同じ原則から違う結論が出ている。

**付随する判断**: ビューに `security_invoker = on` を付ける。ビューは既定でビュー所有者の権限で実行され、元テーブルの RLS を迂回する。権限の境界を DB に置く設計上、ビューだけ例外にはできない。

---

## 8. 観測ログはアプリから書けない

**決定**: `checks` には INSERT / UPDATE / DELETE のポリシーを一切作らず、書き込みを `record_check()`（SECURITY DEFINER）だけに絞る。あわせて `monitors` の判定キャッシュ列（`current_status` など）を列単位の GRANT から外す。

**理由**: 稼働率は「このログを誰も書き換えていない」ことの上に成り立つ数字でしかない。画面から `current_status = 'up'` と書ける経路が1つでもあれば、「落ちているのに正常と表示される」状態をアプリのバグとして作り込める。

RLS は「どの行に触れるか」しか決められないので、「どの列を書き換えてよいか」は GRANT で決める。

---

## 9. 判定規則を DB と TypeScript の両方に持つ

**決定**: 状態遷移の規則を `record_check()`（SQL）と `nextMonitorState()`（TS）の両方に置く。

**これは重複だが、役割が違う**

|       | 役割                                                     |
| ----- | -------------------------------------------------------- |
| DB 側 | 規則を**守らせる**。どの経路から記録しても同じ結果になる |
| TS 側 | 規則を**検証する**。DB を立てずにテストできる            |

判定の規則はこのツールの中核で、間違えると「落ちているのに気付かない」に直結する。その規則を、DB を起動しないと確かめられない場所だけに置きたくない。

**ずれのリスクへの対処**: TS 側に閾値1・閾値3・unknown からの遷移を網羅したテストを置き、SQL 側の `case` 式と一対一で対応させた。片方だけを変えればテストが落ちる。

---

## 10. 監視対象の URL を入口で検証する

**決定**: `http` / `https` 以外、URL 内の認証情報、localhost・私有 IP・リンクローカルを弾く。

**理由**: このツールは「利用者が入力した任意の URL に、サーバー側からリクエストを送る」という、SSRF そのものの形をしている。送信元が Cloudflare Workers なので社内ネットワークには到達しないが、それは実行環境がたまたま守ってくれているだけで、設計として守っているわけではない。

Phase 3 で公開ステータスページを出す以上、「自分以外の誰かが登録した URL」を踏む可能性は将来必ず出てくる。

**この検証で防げないこと**: ホスト名だけを見る検証は DNS リバインディングを防げない（登録時は公開 IP、チェック時は私有 IP を返す名前がありうる）。ここで防げるのは「明らかに内部を指す入力」までで、そこは割り切っている。

**あわせて**: URL 内の認証情報を弾くのは SSRF ではなく別の理由で、DB に平文で残り画面にも出るため。監視のためにそこまで預かる必要はない。

---

## 11. チェック間隔を選択肢に限る

**決定**: 60 / 300 / 900 / 1800 / 3600 秒のいずれかだけを許す（DB の CHECK 制約でも縛る）。

**理由**

1. Cron は1分ごとにしか起動しない。それより短い間隔は構造上実現できず、入力できてしまうと「設定したのに守られない」設定になる。
2. 監視対象から見れば、チェックは外部から来るトラフィックそのもの。10 秒間隔のような値を許すと、監視が相手の負荷になる。

既定値を最短（1分）ではなく5分にしているのも同じ理由。短くするのは必要になってからでよい。

---

## 12. 観測ログに保持期間を設ける

**決定**: 30日を超えた `checks` を1日1回削除する（`purge_old_checks()`）。

**理由**: 1対象を1分間隔で監視すると年間50万行を超える。画面が使うのは直近7日ぶんなので、無期限に持つ理由がない。

**採らなかった案**: _消す前に日次へ集約して残す_ — 長期の稼働率を残せるが、「1年前の月次稼働率を見たい」という要求はまだ無い。今作ると、使われない集約テーブルと、その整合を保つ責任だけが残る。

**判断が変わる条件**: 月次・年次の稼働率レポートが必要になったとき。そのときは集約テーブルを追加し、保持期間はそのままにする。

---

## 13. `checks.id` を uuid にしない

**決定**: `bigint generated always as identity` を使う。

**理由**: このテーブルは時系列に追記され続けるログで、1対象あたり年間50万行に達する。uuid は 16 バイトでランダムな順序に挿入されるため、索引の断片化を招く。外部に露出する識別子でもないので、推測されにくさは要件にならない。

`monitors` の方は uuid のまま。こちらは Phase 3 で公開ステータスページの URL に載る可能性があり、連番だと他人の監視対象の存在と数が推測できてしまう。

---

## 14. Next.js ではなく Vite

**決定**: React + TypeScript + Vite。静的ビルドを CDN に配信する。

**理由**: Phase 1 の画面は認証の内側だけで動き、SEO も OGP も不要。権限の境界を RLS に置く設計上、サーバー層そのものが要らない。サーバーが必要な唯一の部分（定期実行）は Cloudflare Workers が担当する。

**判断が変わる条件**: **Phase 3 の公開ステータスページ**。認証不要で外部に共有される画面なので、OGP と初期表示速度が意味を持つようになる。ただしその1画面のために全体を移すのは割に合わないので、まずは「Workers で静的に描いて返す」か「クライアント描画のまま OGP 画像だけ Workers で生成する」を検討する。Next.js への移行はその次の選択肢。

---

## 15. モックモードを画面の外側の層として持つ

**決定**: `lib/data-source.ts` にデータ取得の境界を置き、Supabase 実装とモック実装を差し替える（`VITE_USE_MOCK`）。

**採らなかった案**

- _各画面で `if (isMockMode)` と分岐する_ — 分岐が画面の数だけ増え、どこかで必ず書き漏らす。
- _モックを持たない_ — DB と Worker を動かさないと画面が1つも見られない。デモ、スクリーンショット、初見の人の動作確認のすべてが止まる。

**この層に置かないもの**: 整形・判定・集計はここに書かない。それらは `@statuspulse/core` にあり、モックと本番で同じ関数を通る。モック側が稼働率の集計を独自に持つと、モックで確かめた意味が無くなる。実際、モックの状態判定も本番と同じ `nextMonitorState()` を先頭から流して求めている。

---

## 16. テストを判定ロジックに絞る

**決定**: `packages/core` の純粋関数だけをテストする。画面のスナップショットや CRUD の往復は書かない。

**理由**: テストの価値は「壊れたときの被害 ÷ 維持コスト」で決まる。ダウン判定と稼働率の計算は、間違えると**このツールの存在理由そのものが失われる**（落ちているのに気付けない、落ちていないのに呼び出される）一方、規則が安定しているので維持コストが低い。画面のスナップショットは逆で、被害が小さく、変更のたびに壊れる。

**判断が変わる条件**: `record_check()` 自体の振る舞い（同時実行時の行ロック、連続失敗カウントの競合）を検証したくなったら、テスト用 DB に対する統合テストを別に追加する。Phase 2 の Slack 通知は、送信の冪等性が DB の一意制約に依存するため、そこは統合テストが必要になる可能性が高い。

---

## 17. ダウンタイムをテーブルとして持つ（Phase 2）

**決定**: `incidents`（`started_at` / `ended_at`）を作り、`record_check()` が開閉する。

**採らなかった案**

- _`checks` から都度導く_ — 連続した失敗のまとまりは SQL で取り出せる（gaps and islands）ので、テーブルを増やさずに済む。実際シードではその方法を使っている。
- _画面側で並びを見て判断する_ — 7日ぶんのチェックをブラウザへ運ぶことになり、Phase 1 で否定した構造に戻る。

**理由**: 3つあり、いずれも「**安定した ID が要る**」ことに帰着する。

1. 通知の重複判定に「この障害」を一意に指す鍵が要る（判断 20）
2. 保持期間（30日）を過ぎて `checks` が消えても、障害の記録は残したい
3. Phase 4 のポストマーテムをぶら下げる先になる

導出できることと、導出し続けるべきことは別。

## 18. インシデントの開始は「最初の失敗」、終了は「成功を確認した時刻」

**決定**: `started_at` は連続失敗の1回目の時刻。`ended_at` は復旧を確認したチェックの時刻。

**理由（開始側）**: 閾値を N にすると down と判定されるのは N 回目だが、**実際に落ちていたのは1回目から**。判定の時刻を起点にすると、ダウンタイムが「間隔 × (N−1)」ぶん短く記録される。

誤検知を減らすための設定が、稼働率を良く見せる方向に働いてはならない。そのために `monitors.first_failure_at` を持ち、成功したら NULL に戻す。

**理由（終了側）**: 実際に直ったのは「最後の失敗」と「最初の成功」の間のどこかで、正確には分からない。監視できていない区間を「直っていた」側に数えると稼働率が実態より良くなるので、疑わしい区間はダウン側に入れる。

これも判断 6（切り捨て）と同じ方針で、**誤差は必ず悪い側に倒す**。

---

## 19. 継続中のインシデントは DB 側で1本に制限する

**決定**: `create unique index incidents_one_open_per_monitor on incidents (monitor_id) where ended_at is null;`

**理由**: 「1つの監視対象に、継続中の障害は1本まで」はこのモデルの不変条件で、破れると稼働率が二重計上される。`record_check()` のロジックが正しければ破れないが、**ロジックが正しいことに依存しない**のが DB に制約を置く意味になる。

Phase 1 で `checks` を読み取り専用にしたのと同じ考え方。アプリのコードを信頼の前提に置かない。

---

## 20. 稼働率を時間ベースへ移した（判断5の条件到達）

**決定**: 稼働率 = 1 − 停止していた時間 ÷ 監視できていた期間。

**理由**: 判断5に「Phase 2 でダウンタイム履歴を持った時点で移す」と書いた条件に到達した。

チェック回数ベースは「チェックの 0.5% が失敗した」という意味しか持たず、他のサービスが出す稼働率（時間ベース）と比較できない。「停止 37分」と書ける方が、影響の大きさがそのまま伝わる。

**回数も残す**: 分母がどれだけの観測に支えられているかは、稼働率とは別に知る必要がある（12回中の 100% と 2016回中の 100% は重みが違う）。画面では回数を補助として併記している。

**この定義でも残る弱点**: どちらの定義も「監視できていた時間」の話でしかない。定期処理自体が止まっていれば、その間の障害は `incidents` にも `checks` にも現れない。判断5で入れた `checkCoverage()` の警告は、そのまま残してある。

---

## 21. 通知の重複防止は incident の ID を鍵にする

**決定**: `notifications.dedupe_key` を `monitor_down:<incident_id>` の形にし、一意制約で重複を弾く。

**採らなかった案**

- _前回の実行時刻からの差分を見る_ — 実行が飛べば取りこぼし、二度走れば重複する。Cron は同じ時刻に二度走ることがあり、手動実行や再デプロイでも重複しうる。
- _日付で区切る（`monitor_down:<監視対象>:<日付>`）_ — 1日に2回落ちたときに2回目が通知されない。

**理由**: 障害そのものに紐づく鍵なら、いつ何度走っても結果が同じになる。「同じ障害は1回だけ」という意図が、そのまま鍵の形になっている。

**付随する判断 — 送信より先に記録する**: 逆順にすると、送信成功後に記録へ失敗したときに二重送信になる。この順序だと送信失敗時に通知が欠けるが、欠けたことは `status = 'failed'` として画面に残るので、黙って消えることはない。

**判定と記録を1つのクエリにする**: `insert ... on conflict do nothing` の結果で判定する。「送ったか確認する」と「記録する」を分けると、その隙間で複数の Worker が両方とも「まだ送っていない」と判断しうる。

## 22. 連続失敗の閾値を既定 2 にし、検知の遅れを画面に出す

**決定**: `failure_threshold` の既定値を 1 から 2 に変え、設定画面に「検知が最大 N 分遅れる」と表示する。

**採らなかった案**: _既定を 3 にする_ — 誤検知はさらに減るが、閾値 N は検知の遅れを「間隔 × (N−1)」まで伸ばす。1時間間隔の対象を 3 にすると**最大2時間気付けない**。

**理由**: 2 は「もう一度確かめてから言う」の最小形で、遅れも1回ぶんに収まる。

**遅れを画面に出す理由**: 閾値は「大きいほど安全な設定」ではない。選ぶ時点でトレードオフを数字にしないと、利用者は選べない。設定画面では選択と同時に `detectionDelaySeconds()` の結果を出し、通知本文にも「2回連続で失敗（最大 10分 の検知遅れ）」と書いている。

**判断が変わる条件**: 1回のチェックの中で数秒おいて再試行する方式（外形監視サービスの多くが採る）を入れたら、閾値を上げずに誤検知を減らせる。ただし Worker の実行時間を消費するため、対象数とのバランスで決める。

---

## 23. 復旧も必ず通知する

**決定**: ダウンだけでなく復旧も Slack に流す。

**理由**: ダウンの通知だけを流すと、Slack を見ても「まだ落ちているのか、直ったのか」が分からない。障害対応で最も無駄が出るのは、**すでに直っているものを追いかける時間**になる。

復旧の通知には停止していた時間を入れる。事後に最も参照される数字がそれだから。

**継続中は鳴らさない**: 通知は状態が変わった回だけで、落ち続けている間は沈黙する。同じ障害を何度も流すと、受け取る側は通知そのものを見なくなる。

---

## 24. 公開ページは「テーブルを開く」のではなく「関数を開く」（Phase 3）

**決定**: 匿名ユーザー（`anon`）に開くのは `public_status(slug)` 1つだけ。テーブルは1枚も開かない。

**採らなかった案**

- _`status_pages` と `monitors` に anon 向けの RLS ポリシーを足す_ — 一見自然だが、RLS のポリシーは**引数を取れない**。`using (exists (select 1 from status_pages sp where sp.monitor_id = monitors.id and sp.is_published))` と書くと、anon は「公開中の監視対象」を**全件列挙できる**。他人の公開ページと、その監視先 URL まで引ける。公開ページが公開情報であることと、公開ページの一覧が公開情報であることは別。
- _署名付きトークンを検証する Edge Function を置く_ — 実現できるが、Supabase の外に層が増える。RLS に権限の境界を置く構成の利点が薄れる。

**理由**: slug を「知っていること自体が権限」として扱うなら、鍵を引数で受け取る入口が要る。RLS は「この人が触れる行はどれか」を答える仕組みで、「この鍵に対応する行はどれか」を答える仕組みではない。**問いの形が違うものを、同じ仕組みで解こうとしない。**

**代償**: 公開ページに出す項目を増やすたびに関数を書き換えることになる。ただしそれは欠点というより、**出す情報を1か所でしか決められない**という性質でもある（判断 26）。

---

## 25. 公開 URL に監視対象の ID を使わない

**決定**: `status_pages.slug`（22文字、約111ビット）を別に持つ。

**理由**

1. **取り消せない**。URL が漏れたとき、ID を使っていると無効化する手段が「監視対象ごと作り直す」しか残らない。slug なら再発行できる（`rotate_status_page_slug()`）。
2. 内部 ID を外に出すと、その ID が他の経路で意味を持ったときに影響が広がる。

**付随する判断**: 使う文字から `l` `1` `0` `o` を外した。この URL は口頭で伝えたりチャットに貼られたりするもので、読み違いが起きる文字を含めたくない。

**公開停止と再発行を別の操作にしてある**理由も同じところにある。公開を止めるだけでは、再開したときに同じ URL が生き返る。漏れた URL を無効にしたいなら slug そのものを変えるほかない。画面ではこの使い分けを、再発行の確認文に書いている。

## 26. 公開ページでは「何を出さないか」を先に決める

**決定**: `public_status()` は次を返さない。

| 出さないもの     | 理由                                                 |
| ---------------- | ---------------------------------------------------- |
| 監視先の URL     | `/health?token=...` のような経路が設定されうる       |
| `error_message`  | スタックトレースや内部ホスト名が入りうる             |
| `status_code`    | 利用者の行動を変えないが、内部構成の手がかりにはなる |
| 監視対象の内部名 | 公開用のタイトルを別に持つ（`status_pages.title`）   |
| 所有者・メンバー | 誰が運用しているかは公開情報ではない                 |

出すのは「今動いているか」「どれだけ止まっていたか」「いつ止まっていたか」と応答時間だけ。

**応答時間は出す**。速さは利用者の体感そのもので、隠す理由が無い。

**TypeScript 側の型も、出してよいものだけの形にしてある**（`PublicStatus`）。管理画面の型を流用すると、余計な項目を持ったまま公開画面へ渡す経路ができてしまう。

---

## 27. 情報が古いときは「正常」と言い切らない

**決定**: 最終チェックから「間隔 × 3」を超えていたら、`up` であっても公開ページの見出しを「状態を確認しています」に落とす。

**理由**: 公開ページで最も避けたいのは、**定期処理が止まっているのに「正常に稼働しています」と出し続けること**。見に来た人はその表示を信じて、それ以上確かめない。管理画面なら運用者が気付けるが、公開ページの読み手は気付けない。

3倍にしているのは、1回の取りこぼしや Cron のゆらぎで「確認中」が出ないようにするため。

**落ちている表示も同じ扱いにする**。情報が古ければ「障害中」とも言い切らず「確認中」に寄せる。直っているのに落ちていると言い続けるのも、同じ種類の嘘になる。

## 28. RLS の再帰を SECURITY DEFINER 関数で断つ

**決定**: 役割の判定を `can_view_monitor()` / `can_edit_monitor()` / `is_monitor_owner()` に切り出し、ポリシーからはこれらだけを呼ぶ。

**理由**: `monitors` のポリシーが `monitor_members` を参照し、`monitor_members` のポリシーが `monitors` を参照すると、ポリシーの評価が互いを呼び合って無限再帰する（Postgres は 42P17 で止める）。SECURITY DEFINER 関数は定義者の権限で走るため RLS を通過し、この輪を断てる。

**この関数に持たせなかったもの**: 引数は監視対象だけで、ユーザーは常に `auth.uid()` を見る。「任意のユーザーの役割を返す関数」にすると、RLS を迂回して他人の権限を調べる道具になる。**SECURITY DEFINER 関数は、できることを最小にして初めて安全になる。**

あわせて、これらの関数の EXECUTE を `anon` から剥がしてある。判定にしか使わないので anon から呼べる必要が無い。

## 29. 役割を3段階にし、最後の owner を DB で守る

**決定**: `owner` / `editor` / `viewer`。owner だけが削除・共有設定・公開ページの発行をできる。

**editor に削除を許さない理由**: 監視対象の削除は、チェック履歴とダウンタイムの記録を巻き添えにする。設定の変更と同じ重さの操作ではない。

**最後の owner を降格・削除できないようにする理由**: owner が1人もいない監視対象は、共有設定も削除も誰にもできない状態になり、直す手段が DB を直接触ることしか残らない。**操作できなくなる種類の事故は、起きてからでは戻せない。** `assert_not_last_owner()` で DB 側に置いてある。

**自分で抜けるのは owner でなくても許す**。共有された側が縁を切れないのは不便で、かつ危険でもない（抜けたら見えなくなるだけ）。

## 30. 招待は「登録済みユーザーのメール一致」に限る

**決定**: `add_monitor_member(monitor_id, email, role)` は `auth.users` を引き、見つからなければ `USER_NOT_FOUND` を返す。

**採らなかった案**: _招待トークンを発行してメールを送る_ — 未登録の相手も招待でき、こちらが本来の形。ただしメール送信の経路とトークンの失効管理が要る。

**この割り切りが持つ弱点**: `USER_NOT_FOUND` を返す以上、「そのメールが StatusPulse に登録済みか」が分かる。ただし試せるのはログイン済みのユーザーに限られ、総当たりの速度は Supabase 側のレート制限に依存する。個人〜小規模チーム向けという前提では受け入れられる範囲だと判断した。

**判断が変わる条件**: 不特定多数に開いたサービスにするなら、この関数は成否を返さない形（常に「招待を送りました」と返す）に変え、招待トークン方式へ移す。
